# Recovery Card — 손상 영상 수리와 단편화 복구

## 구현 승인 후 변경된 요구 (2026-10-17, 아래 초기안보다 우선)

사용자는 구현을 승인한 뒤 ‘우리만의 엔진’과 논문을 참고한 개발을 요청했다. 이에 untrunc 연동은 구현하지 않는다. 자체 Rust 코드로 exFAT 체인과 컨테이너·NAL 구조를 분석한다. FFmpeg/ffprobe는 복구된 압축 비디오의 표준 컨테이너 저장과 독립 디코딩 검증에만 사용한다.

첫 자체 수리 방식은 정상 참고 MOV/MP4의 avcC/hvcC 파라미터를 읽고, 손상 대상의 길이 접두사 NAL 및 access-unit 경계를 검사하여 H.264/HEVC 압축 비디오를 구조적으로 구출하는 것이다. 알려지지 않은 바이트를 건너뛴 범위와 사용한 원본 바이트 범위를 기록하고, 독립적으로 재생 가능한 키프레임부터 시작한다. 오디오·원래 타임스탬프 복원은 이 방식에서 보장하지 않으며 반드시 ‘영상 트랙 부분 복구’로 표시한다. 프레임률은 참고 영상에서 가져온 추정임을 보고한다. 물리 조각의 순서는 exFAT 체인이 있을 때만 복원한다. 원본 바이트나 프레임을 생성하는 AI 보정은 넣지 않는다.

이 추가 요구는 아래 A의 외부 수리 엔진 항목을 대체한다. B의 exFAT 복구, 안전한 저장, 앱 연결, 검증 요구는 유지한다. 메타데이터 기반 무손실 추출은 오디오와 원래 타임스탬프를 포함한 원본 컨테이너 바이트를 보존한다. 자체 알고리즘의 세계 최초 여부나 기존 도구 대비 우월성을 주장하지 않고 공개 합성 정답과 실패 사례로 검증한다.

## 목적과 현재 상태

사용자가 2026-10-17 요청한 ‘마지막 단계’는 직전 평가의 손상·분할 영상 복구다. macOS, Fujifilm X-T5, 외장 SSD 저장이라는 기존 조건을 유지한다. 이 문서는 기존 다중 형식 설계에서 나중으로 미뤘던 영상 복구 기능의 구체적인 범위를 정한다. 사진 엔진 개선이나 GitHub 공개를 이번 요청에 포함시키지 않는다.

현재 제품은 SwiftUI + Rust의 JPEG/RAF 검색·추출 앱이다. 영상 복구·전체 디코딩은 제품 밖에서 수행했다. 실제 카드에서 찾은 두 MOV는 모두 정상이며, 이번 작업에 사용할 실제 손상 영상은 아직 확인되지 않았다. 실제 카드 이미지에서 exFAT, 512바이트 섹터, 128KiB 클러스터, 단일 FAT를 확인했다. 두 영상에는 각각 ftyp → moov → mdat가 있고 HEVC가 들어 있다. 이 관찰을 모든 X-T5 설정의 보장으로 확대하지 않는다.

사용자에게 별도의 손상 영상이 있는지 물었다. 없다면 외장 SSD에 만든 정상 영상 복사본과 공개 가능한 합성 영상으로 손상을 재현한다. 실제 미디어·이미지·개인 경로는 저장소에 넣지 않는다.

## 이번 버전의 사용자 경험

기존 사진 복구 화면에 ‘영상 복구’ 작업을 추가한다. 사용자는 다음 두 작업 중 하나를 선택한다.

1. **손상 영상 수리:** MOV/MP4 파일, 같은 카메라·코덱·해상도·프레임률·오디오 설정의 정상 참고 영상, 저장 폴더를 선택한다. 사전 분석 → 수리 → 전체 영상/음성 검사 → 결과 보고 순서로 동작한다. 헤더가 없는 대상의 촬영 설정은 알 수 없으므로 일치 여부를 확정했다고 표시하지 않는다.
2. **카드 이미지의 영상 조각 복구:** 평면 이미지 파일과 저장 폴더를 선택한다. exFAT 디렉터리 정보와 FAT 체인을 읽어 MOV/MP4 후보를 제시한다. 선택한 후보의 클러스터들을 원래 논리 순서대로 추출하고 검사한다. 원래 이름이 남아 있으면 참고 정보로 표시하되, 출력 이름은 생성한 식별자를 사용한다.

입력 선택, 작업 시작, 진행 단계·경과 시간, 취소, 결과 목록, 저장 폴더 열기를 제공한다. 읽기·복사처럼 총량이 알려진 구간에만 바이트 진행률을 표시한다. 외부 수리 엔진의 진행률은 임의 추정하지 않는다. 외부 도구가 없으면 해당 작업의 시작을 막고 설치·경로 설정 안내를 표시한다.

## A. 재생 정보가 사라진 MOV/MP4 수리

- 별도로 설치하거나 지정한 `anthwlock/untrunc` 실행 파일을 사용한다. 정상 참고 영상에서 트랙 정보를 얻고 손상 파일의 미디어 데이터를 분석하는 방식이다. 단순히 정상 파일의 moov 바이트를 붙이지 않는다.
- Swift의 별도 프로세스 실행으로 연결하고, 셸 문자열을 조합하지 않는다. `-n`, 명시적 `-dst` 출력 경로, 절대 입력 경로를 사용한다. 설치 버전의 옵션 지원을 사전 확인한다. 엔진 바이너리를 앱이나 저장소에 포함하지 않는다.
- 새 세션 안에 작업용 입력 사본을 만들고 그 사본만 엔진에 전달한다. 원본과 참고 영상의 변경 감지 정보를 기록한다. 생성한 사본의 SHA-256을 원본을 읽으며 계산한 값과 비교한다. 외장 SSD에 필요한 공간을 시작 전과 실행 중 확인한다.
- 기본 시도는 보수적인 수리다. 알 수 없는 데이터를 건너뛰는 모드는 별도의 ‘부분 복구 시도’로 명시하고 출력도 별도로 보존한다. 임의의 프레임 생성, 자동 재인코딩, 오디오 길이에 맞추는 자동 속도 변경은 하지 않는다.
- 참고 영상은 디코딩 가능한 영상 트랙이 있어야 한다. 참고 파일을 대상 파일과 동일한 것으로 선택하는 것은 제품에서 거부한다. 엔진 실패·출력 부재·검증 실패를 성공으로 처리하지 않는다.
- HEVC/H.264 및 오디오 설정별로 실제 성공 사례를 기록한다. untrunc가 지원한다고 추정하는 것만으로 X-T5 모든 모드 호환을 표시하지 않는다. 개발 환경의 FFmpeg 8.1과 엔진 빌드 호환성을 실제 검사한다.

## B. exFAT의 저장 순서를 이용한 조각 복구

- Rust 엔진에 읽기 전용 exFAT 분석을 추가한다. 초기는 단일 FAT exFAT 볼륨과 MBR의 exFAT 파티션을 지원한다. GPT, FAT32, TexFAT는 ‘지원하지 않는 레이아웃’으로 분명하게 반환한다. 지원 범위 밖을 전체 검색 실패로 표시하지 않는다.
- 부트 영역의 서명·필드 범위·체크섬을 확인한다. 주 부트가 손상된 경우 유효한 백업 부트를 사용할 수 있고 그 근거를 보고한다. 섹터 크기·클러스터 크기·FAT·힙·루트 위치에 대해 이미지 내부 범위와 정수 오버플로를 검사한다.
- 유효한 디렉터리에서 파일 엔트리 집합과 stream extension을 읽는다. 활성 엔트리는 집합 체크섬을 검사한다. 삭제 엔트리는 InUse 비트를 복원한 체크섬과 필수 엔트리 순서를 검사하되 ‘삭제 흔적’으로 낮은 확신도를 유지한다. 처음부터 데이터 영역의 임의 바이트를 디렉터리라고 해석하는 휴리스틱은 넣지 않는다.
- NoFatChain이 설정된 파일은 선언된 연속 범위를 읽는다. 그 외에는 FAT의 다음 클러스터 값을 따라 여러 조각을 논리 순서로 구성한다. 루프, 중복, 범위 이탈, 잘못된 종단, 필요한 길이보다 짧은 체인을 거부한다. bitmap 할당 여부와 발견 근거를 기록하고 재할당 가능성을 숨기지 않는다.
- 디렉터리 순회는 이미지 범위·방문 집합·총 엔트리·깊이 한도를 둔다. 파일과 디렉터리에 대한 순환 체인은 즉시 중단한다. 크기가 큰 영상을 RAM에 전부 읽지 않는다.
- MOV/MP4 확장자는 후보 필터일 뿐이며, 복원된 시작 부분의 컨테이너 구조를 추가 확인한다. 메타데이터가 주장하는 이름이나 정상 헤더만으로 복구 완료를 판단하지 않는다.
- 추출 요청에는 논리 순서의 `{offset, length}` 목록과 입력 식별정보를 담는다. 엔진이 요청의 전체 범위와 합계를 다시 검증한다. 기존 512MiB 사진 후보 한도를 영상에 그대로 적용하지 않고 파일 크기와 출력 공간을 기준으로 스트리밍한다.
- 체인이 소실되거나 다른 파일에 재할당되어 순서를 확정할 수 없는 경우 ‘조각 순서 확인 불가’로 남긴다. 빈 영역이나 비슷한 프레임으로 누락 데이터를 채우지 않는다. 복구할 수 없는 후보와 이유도 보고서에 남긴다.

## 첫 버전에서 약속하지 않는 범위

FAT와 디렉터리 정보가 사라진 상태에서 순서를 알 수 없는 조각을 임의 개수로 자동 재조립하는 기능은 별도 연구 단계다. 이번 버전의 ‘단편화 복구’는 살아 있는 메타데이터에 근거한 체인 복구다. PhotoRec의 ftyp/mdat 두 조각 결합은 제한적인 별도 방법이며, 이름이나 가까운 위치만으로 자동 짝짓기하지 않는다. 이를 모든 카메라의 단편화 복구라고 부르지 않는다.

실제 카드에 이런 복구 근거가 남아 있는지는 전체 디렉터리 분석 후에 판단한다. 정상 복구된 영상 2개가 있다는 사실로 추가 삭제 영상이 없다고 결론 내리지 않는다. 덮어쓴 바이트, 암호화, 물리 장애 복제, 모든 RAW/문서 형식 확장은 이번 기능의 완료 기준이 아니다.

## 결과 검증과 상태

`ffprobe`로 컨테이너·트랙을 검사한 뒤, `ffmpeg`로 모든 영상 트랙과 존재하는 모든 오디오 트랙을 끝까지 디코딩한다. 네트워크 입력과 외부 미디어 참조를 허용하지 않는 설정을 사용하고, 코덱·크기·자원 한도 및 시간 제한을 둔다. 프레임 검사는 병렬 실행 수를 제한한다. 사용자 파일은 업로드하지 않는다.

상태는 ‘후보 발견’, ‘수리 결과 생성’, ‘전체 디코딩 통과’, ‘부분 복구·검사 오류’, ‘검사 미완료’, ‘복구 불가’로 구별한다. 프로그램 종료 코드만으로 정상 판정하지 않는다. 생성된 영상 프레임 수가 0이면 실패다. 트랙별 길이·프레임 수·검사 오류·재생 가능한 구간을 기록하며, 헤더가 없어 기대 길이를 모르면 ‘원본 길이 미상’이라고 표시한다. 전체 디코딩 통과도 원본의 모든 장면 보존이나 A/V 동기 정확성 보증은 아니다.

세션 보고서에는 입력과 출력 SHA-256, 실행 도구의 버전, 적용한 복구 방식, 추출 범위, 발견 근거, 검사 결과, 실패 이유를 기록한다. 누락 여부를 확정할 수 없는 데이터는 ‘완전 복구’로 부르지 않는다. 알려진 합성 정답에 대해서만 해시·프레임·오디오의 동일성을 비교한다.

## 저장·취소·실패 처리

- 매번 고유한 새 세션 디렉터리를 생성한다. 입력이나 기존 결과를 덮어쓰지 않는다. 입력은 일반 파일만 허용하고 심볼릭 링크·장치·FIFO를 거부한다. 결과 경로의 링크와 세션 경계 이탈도 거부한다.
- 시작부터 `INCOMPLETE` 표식을 두고, 결과와 보고서 기록이 모두 끝나야 제거한다. 실패·취소된 출력은 남겨 두되 정상 결과 목록에 섞지 않는다. 입력이 변경되면 작업을 실패 처리한다.
- 프로세스와 해당 하위 프로세스의 취소를 함께 처리한다. 정해진 유예 후 강제 종료하고, 출력 수집을 종료해 대기 상태가 남지 않게 한다. 엔진 시작 실패, 잘못된 응답, 공간 부족, SSD 분리, 시간 초과를 각각 사용자 메시지와 로그로 남긴다.
- 새 영상 출력은 세션 안에서 한 번 스트리밍 기록하고 완료 표식으로 게시 상태를 관리한다. 지원하지 않는 exFAT 원자적 rename에 의존하거나 영상 전체를 두 번 복사하는 출판 경로를 기본값으로 삼지 않는다. 완료 전 파일이 보일 수 있음을 보고서와 UI 상태로 처리한다. 기존 사진 exporter 변경은 별도다.

## 테스트와 완료 기준

1. 공개 가능한 H.264/HEVC 합성 영상으로 정상 입력, moov 유실, 뒤쪽 잘림, 잘못된 참고 영상, 0바이트·오인 헤더·지원하지 않는 코덱을 검사한다. 정상 참고 영상과 손상 대상의 원본은 서로 다른 클립이어야 한다.
2. 합성 exFAT 이미지에 서로 떨어진 여러 클러스터로 영상을 저장하고, 논리 순서와 물리 순서를 다르게 한다. 정상·삭제 엔트리, 연속 파일, NoFatChain, 순환/짧은/범위 이탈 체인, 잘못된 엔트리·부트 체크섬, 재할당된 클러스터를 검사한다. 메타데이터가 없는 경우에는 복구 불가 또는 근거 부족으로 반환해야 한다.
3. 무손실 추출 fixture는 원본 파일과 SHA-256이 같아야 한다. 헤더 수리 fixture는 모든 기대 영상 프레임과 오디오가 디코딩되고 사전 기록한 정답과 비교되어야 한다. 손상 때문에 빠진 구간을 성공 프레임 수에 숨기지 않는다.
4. 실제 X-T5 영상은 외장 SSD의 사본만 변형한다. 현재 두 영상은 프레임률·오디오 구성이 달라 서로 적합한 참고 영상으로 단정할 수 없다. 동일 원본을 참고로 쓴 실험은 구조 복원 자기검사로만 보고하며, 다른 정상 클립으로 성공한 것과 구분한다. 실제 손상 사례가 없으면 그 한계를 남긴다.
5. 엔진 없음, 한글·공백 경로, 취소, 프로세스 실패·정지, 링크·기존 출력 충돌, 부족한 공간, 입력 변경을 검사한다. 외부 엔진과 공개 fixture로 재현할 수 있는 통합 검사를 제공한다.
6. 기존 Rust/Swift 검사, 추가 회귀 검사, 앱 빌드와 macOS에서의 선택 → 시작 → 취소/완료 → 결과 확인을 통과한다. CLI 전용 실험이나 별도 작업 스크립트를 앱 완료 기능으로 표시하지 않는다.

## 구현자가 정할 사항과 진행 순서

언어와 앱 구조는 유지한다. 별도 프로세스 실행·로그 수집·취소는 기존 Swift 코드와 통합 가능한 최소 구조로 작성한다. exFAT 파서와 범위 추출은 Rust에서 처리한다. 세부 타입, 파서 상한, 작업 제한 시간, 테스트 fixture 크기는 구현자가 정하되 테스트와 문서에 수치와 이유를 남긴다. 외부 바이너리 버전·출처·해시를 기록하고 비호환 버전은 실패로 처리한다.

구현 순서는 (1) 입력·출력·검증 기반과 untrunc 수리, (2) exFAT 조각 추출과 검증, (3) 앱 흐름 연결, (4) 합성/실제 사본 검증과 문서다. 설치나 엔진 연동 자체를 수리 성능의 입증으로 보지 않는다. 모르는 조각을 재구성하는 연구는 이 완료 이후 독립 범위로 다룬다.
