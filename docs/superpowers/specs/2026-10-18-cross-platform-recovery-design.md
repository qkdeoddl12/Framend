# Framend — 범용 파일 복구와 macOS·Windows 공통 앱

상태: 2026-10-18 사용자 승인 후 A/B 구현. macOS 실행 검증을 진행했으며 Windows 실기기 검증은 남아 있다. 실제 결과는 docs/cross-platform-validation.md에서 관리한다.

## 사용자 요구와 목표

사용자는 특정 카메라나 사진가에게 한정되지 않고, 다양한 파일을 macOS와 Windows에서 복구할 수 있게 개선해 달라고 요청했다. 기존 요구인 강력한 자체 복구 엔진, 사진·영상·일반 파일, 진행 상황 표시, 외장 저장장치 출력과 검증 가능한 결과를 유지한다.

제품 목표는 **Framend — 로컬에서 실행하는 파일 복구 도구**다. 카메라 제조사 선택을 시작 조건으로 요구하지 않는다. 입력의 파일시스템과 파일 구조를 탐지하고 사용 가능한 방법을 제시한다. 영상 수리의 참고 파일은 해당 촬영 설정과 호환되어야 한다.

이 문서의 Tauri 선택, 마일스톤 순서, 초기 OS 버전과 형식 우선순위는 구현 담당자의 제안이다. 사용자가 해당 기술이나 세부 범위를 지정한 것은 아니다.

## 현재 코드에서 확인한 출발점

- `engine/src/formats.rs`: JPEG는 제조사 독립적이다. RAW 파서는 RAF뿐이며 전체 RAW 디코딩을 확인하지 않는다.
- `engine/src/exfat.rs`: exFAT 할당·디렉터리 분석이 있지만 추출 후보는 MOV/MP4로 제한한다. 타 파일의 할당 영역도 교차 연결 검사에는 사용한다.
- `engine/src/native_video.rs`: H.264/HEVC 구조를 사용하는 부분 수리로, 후지필름 전용 알고리즘은 아니다. 모든 코덱 설정을 지원하지 않는다.
- `engine/src/source.rs`, `export.rs`, `exfat.rs`, `native_video.rs`: Unix 파일 API와 macOS 전용 `renamex_np`에 의존한다. 현재 Rust 엔진 자체도 그대로 Windows에서 빌드되지 않는다.
- `Sources/RecoveryCore/`: 작업 관리, 영상 도구 실행, 결과 검증, 구간별 출력 안전성 일부가 Swift에 있다. 화면만 바꾸어서는 기능이 이식되지 않는다.
- `Sources/RecoveryCard/`, `Package.swift`: SwiftUI와 macOS 전용 화면이며 X-T5 고정 문구가 있다.
- 기존 실제 데이터 검증은 X-T5 중심이다. 다른 제조사의 정상 동작 근거로 확대 해석하지 않는다.

## 제안 구조

```text
macOS / Windows 공통 화면 — Tauri 2 + TypeScript
                    │ 타입이 정해진 작업·이벤트
Rust 작업 관리자 — 취소, 외부 도구, 검사, 결과 보고서
                    │
Rust 자체 복구 엔진 — 파일시스템 분석 / 형식별 구조 분석 / 영상 부분 수리
                    │
운영체제별 파일 입출력 — macOS / Windows
```

- 기존 Rust 엔진과 JSON Lines CLI를 유지한다. 장치 접근, 복구 판단과 출력 경로 검증을 웹 화면에 맡기지 않는다.
- Tauri를 공통 데스크톱 화면으로 제안한다. 현재 Rust 자산을 활용하며 macOS와 Windows용 설치 파일을 각각 만들 수 있다. 브라우저에 올린 서비스나 원격 업로드 기능은 필요 없다.
- 기존 SwiftUI 앱은 공통 앱의 기능 동등성이 확인될 때까지 회귀 기준으로 유지한다. 이후 기본 배포 경로를 공통 앱으로 전환한다. 두 화면에 새 기능을 영구적으로 이중 개발하지 않는다.
- Swift 작업 관리의 안전성·취소·시간 초과·구간 분리·출력 검사를 Rust로 이전하고 같은 고장 사례로 확인한다. 단순한 UI 재작성으로 처리하지 않는다.
- FFmpeg는 영상 컨테이너 저장과 디코딩 검사에 사용한다. LibRaw는 후속 RAW 디코딩 검사에 사용한다. 둘의 지원 형식 수를 자체 복구 엔진의 지원 수로 광고하지 않는다.
- 외부 도구는 초기에는 사용자가 설치한 실행 파일을 감지하거나 선택한다. 경로·버전을 기록하고 셸 문자열 없이 실행한다. 바이너리 번들은 라이선스와 배포 구성을 정한 후 별도 작업으로 한다.

## 지원을 넓히는 방법

**파일시스템 메타데이터 복구**와 **내용 기반 탐색**을 별도 기능으로 관리한다. 유효한 이름·길이·클러스터 연결이 남으면 파일 종류와 무관하게 바이트를 추출할 수 있다. 메타데이터가 사라지면 형식별 파서가 파일 경계와 유효성을 확인해야 한다. 확장자 추가만으로 새 복구 기능이 생겼다고 표시하지 않는다.

| 대상 | 우선 구현 | 후속 확장과 주의점 |
|---|---|---|
| 일반 파일 | exFAT의 유효한 일반 파일을 종류와 무관하게 추출 | 문서·압축·오디오도 대상이나 내부 형식 검사는 별도 |
| 일반 이미지 | 기존 JPEG/RAF 유지, 연속 PNG 구조·CRC 검사 | TIFF, HEIF/HEIC, WebP 등은 각각 경계 파서와 검증 추가 |
| 오디오 | 연속 RIFF/WAVE의 길이·청크 구조 검사 | 실제 음성 디코딩 성공과 구조 검사를 구별 |
| 카메라 RAW | 메타데이터가 남은 파일 추출부터 확대 | DNG/CR2/NEF/ARW 계열 구조 탐색 후 CR3/RW2/ORF/PEF 등 순차 검증 |
| 영상 | 기존 MOV/MP4 exFAT 추출, H.264/HEVC 부분 수리 유지 | 제조사별 촬영 모드, B프레임, 긴 GOP·단편화 사례 확장 |
| 문서·압축 | exFAT 메타데이터 기반 추출 | ZIP/OOXML/PDF 내용 기반 탐색은 전용 파서·CRC 등 별도 검증 |
| 저장 구조 | 기존 exFAT 볼륨/MBR부터 공통화 | GPT, FAT32, 이후 NTFS/APFS 메타데이터 분석 |

RAW 포맷 안에서도 모델·압축 모드별 구조가 다르므로 지원표는 확장자 단위와 테스트한 모델/모드를 함께 기록한다. 내장 JPEG를 읽은 결과를 RAW 원본 복구 성공으로 간주하지 않는다. 디코더가 없는 형식은 추출 결과를 유지하고 미검증으로 표시한다.

Windows에서 앱이 실행되는 것과 NTFS 삭제 파일을 복구하는 것은 서로 다른 지원 항목이다. macOS에서도 exFAT 디스크 이미지를 처리할 수 있듯 Windows에서도 동일한 이미지 분석을 제공한다. NTFS/APFS를 첫 Windows 버전의 암묵적 지원 범위로 넣지 않는다.

## 운영체제 공통 계약

1. 입력은 읽기 전용의 일반 디스크 이미지와 손상 영상/참고 영상이다. 초기 공통 버전은 물리 드라이브를 직접 열거나 관리자 권한을 요구하지 않는다.
2. 파일 읽기, 원본 식별/변경 확인, 새 출력 생성, 여유 공간 확인, 결과 확정을 플랫폼 모듈로 모은다. Unix 검사 코드를 제거하거나 Windows에서 검사를 생략하지 않는다.
3. Windows 구현은 열린 핸들의 파일 식별정보와 변경 정보를 사용한다. reparse point, 경로 교체, 디렉터리 교체를 검사하고 공유 모드를 명시한다. macOS에서는 기존 보장과 회귀 검사를 유지한다.
4. 기존 파일을 덮어쓰지 않고 새 세션 폴더에 기록한다. EXDEV/파일시스템별 rename 차이를 고려하고 원자적 확정을 지원하지 않으면 배타 생성·복사와 미완료 표식을 사용한다.
5. 한글·공백·긴 경로, 대소문자 충돌, Windows 예약 이름, ADS 구문, 경로 탈출을 처리한다. 원래 파일명은 보고서에 보존하고 출력명은 생성한 안전한 이름으로 사용한다.
6. 취소, 공간 부족, 원본 변경, 도구 시간 초과, 부분 파일은 명시적 상태로 남긴다. 실패를 복구 완료로 표시하지 않는다.
7. 입력과 출력의 파일 식별정보는 같은 OS의 한 작업 안에서 검증한다. macOS 스캔 요청을 Windows에서 그대로 재사용하지 않는다. 공통 비교 대상은 후보의 바이트 범위·형식·결과 해시다.
8. 사용자 파일의 내용·파일명·장치 정보는 네트워크로 보내지 않는다. 공개 테스트에는 합성 데이터와 재배포 가능한 표본만 사용한다.

## 공통 화면과 품질 상태

주요 흐름은 입력 선택 → 저장 폴더 선택 → 검색 → 종류별 후보/검사 수준 표시 → 선택 복구 → 결과/오류 확인이다. 손상 영상 수리는 별도 모드에서 참고 영상을 받는다. 이미지·영상·오디오·문서·압축·기타로 필터링하며 카메라 모델은 발견된 메타데이터로만 표시한다.

진행률은 실제 읽은 바이트를 기준으로 한다. 총량을 모르는 단계는 처리 수와 경과 시간을 표시한다. 입력 보호, 외장 SSD 저장, 취소와 결과 폴더 열기를 두 OS에서 제공한다. 한국어·영어 문자열은 분리한다.

검사 상태는 `구조 확인`, `체크섬 확인`, `디코딩 통과`, `부분 복구`, `미검증`, `검사 실패`를 별도 속성으로 기록한다. 부분 복구와 디코딩 통과는 동시에 성립할 수 있다. 전체 원본의 동일성은 정답 해시가 있는 테스트에서만 판정한다.

## 순서와 완료 기준

### A. 공통 엔진과 첫 범용 파일 지원

- 플랫폼별 I/O를 분리하고 Windows x64 / macOS ARM64·x64용 빌드 경로를 만든다. macOS 14+, Windows 11을 첫 검증 대상으로 제안한다. Windows ARM64·Linux 제품 배포는 후속 범위다.
- 기존 CLI 명령과 Swift 프로토콜을 유지하며, exFAT 일반 파일 검색·추출용 새 명령/보고서를 추가한다. 기존 영상 검색에 일반 파일을 섞어 오래된 화면을 깨뜨리지 않는다.
- exFAT 일반 파일은 할당·길이·겹침 검사에 통과한 후보만 추출한다. 삭제된 체인이 사라졌거나 다른 활성 파일과 겹치면 추측하여 정상 복구로 반환하지 않는다.
- PNG와 WAVE 내용 기반 파서를 추가하고 기존 스캔 호출자는 새 형식을 다룰 수 있게 함께 갱신한다. 알려지지 않은 형식을 조용히 JPEG로 해석하지 않는다.
- **완료:** 두 OS에서 기존 엔진 검사와 새 형식의 정상·손상·잘린 데이터 검사가 실행되고, 같은 합성 이미지의 후보 범위와 출력 SHA-256이 일치한다. Windows CI 설정만 작성한 상태는 완료가 아니다.

### B. 공통 데스크톱 앱

- Rust 작업 관리자와 Tauri 화면을 추가한다. 검색, 선택 복구, 영상 구간 수리, 검사·로그·취소·공간 부족 처리까지 이전한다.
- 사진 미리보기의 ImageIO 의존성을 대체한다. 지원하는 래스터 이미지만 제한된 크기로 디코딩하며 RAW 미리보기는 RAW 전체 검사와 구분한다.
- 공통 보고서에 스키마 버전을 넣고 이전 결과를 열거나 호환되지 않음을 명확히 알린다. 기존 증거 파일과 원본은 자동 변경하지 않는다.
- **완료:** macOS·Windows에서 파일 선택부터 결과 확인까지 실행하고, 취소·시간 초과·손상 입력·원본/출력 교체 회귀 검사가 통과한다. macOS `.app`/`.dmg`, Windows 설치 파일을 각 OS에서 빌드한다. 서명·공증 여부를 별도로 표시한다.

### C. 카메라·저장 구조 확장

- FAT32/GPT, RAW 계열 파서와 LibRaw 검사, 추가 미디어·문서 형식을 순차 추가한다. 각각 구조가 분명한 범위부터 지원표에 올린다.
- Canon·Nikon·Sony·Panasonic·OM System·Pentax·Fujifilm 및 스마트폰/액션캠 표본을 수집하되, 합법적으로 재배포 가능한 데이터만 공개 fixture로 넣는다.
- 정상 삭제, 빠른 포맷, 헤더 손상, 꼬리 손상, 파일 조각 분리, 덮어쓰기 사례를 구분한다. 지원하지 않는 단편화는 별도로 집계한다.
- **완료:** 형식별 지원 상태, 실제 표본/합성 여부, 바이트 동일 추출 수, 디코딩 성공·부분 복구·오탐 수, 처리량·최대 메모리를 공개한다. 형식마다 통과한 범위만 지원한다고 표시한다.

초기 공통 배포는 A와 B가 모두 끝난 상태다. C 전체를 완료해야만 첫 공통 앱을 배포할 필요는 없다. 물리 장치 복제/재개, NTFS/APFS 전용 분석, AI 조각 순위화는 이후 독립 마일스톤이다. AI로 만들어낸 픽셀을 원본 복구로 표시하지 않는다.

## 검증과 배포 경계

- OS별 CI는 네이티브 runner에서 실행한다. Windows 기능은 이 Mac에서의 교차 컴파일만으로 검증 완료 처리하지 않는다.
- 기존 0.3의 사진·exFAT·영상 구간 검사를 유지하고, 일반 파일 추출은 확장자와 무관하게 바이트 해시를 비교한다. PNG CRC와 ZIP 등의 내부 무결성은 서로 다른 검사다.
- I/O 검사에는 링크/reparse point, 입력 교체, 출력 폴더 교체, 출력 파일 교체, 기존 파일 보존, 디스크 부족, 취소, OS별 예약 이름을 포함한다.
- GitHub 저장소 생성·공개 push·릴리스 게시, 배포 서명 계정 구매는 이번 설계가 자동으로 수행하는 작업이 아니다.
- 과거의 PhotoRec 연동 설계와 실제 0.3 자체 엔진은 구별한다. 본 확장은 자체 엔진을 중심으로 하며 미구현된 과거 계획을 완료 기능으로 승계하지 않는다.
